## 2. Кейс C-1

Конфлікт критеріїв: П'ять із шести критеріїв однозначно тягнуть у предиктивний бік. Вимоги зафіксовані офіційним наказом регулятора заздалегідь, замовник приймає роботу формальними триетапними актами й не ходить на демо, контракт укладено за тендером на fixed price із жорсткою пенею, а помилка веде до зриву законодавчого терміну подання. Конфліктує з ними виключно технологія: API реєстру нове, нестабільне, доступне лише в пісочниці, двічі змінювалося без попередження, а техпідтримка відповідає тижнями. Переміг предиктивний підхід, оскільки юридичні рамки тендерного договору та незмінний строк здачі виключають гнучкість обсягу.

Що робимо з критерієм, який тягне проти: Повністю ізолюємо інтеграційний контур: розробляємо власний локальний мок-сервер (емулятор) API реєстру на базі опублікованих специфікацій і закладаємо додатковий часовий буфер перед фінальною здачею для налагодження взаємодії з бойовим контуром.

Відкинутий підхід: Адаптивний підхід. Плюс: дозволив би гнучко реагувати на раптові зміни поведінки API реєстру в кожній ітерації. Мінус: повністю руйнує фіксовані терміни тендерного договору та вимагає постійної участі контактної особи замовника, яка відмовилася від щотижневих демо.

Перший тиждень: Створити технічний спайк для перевірки реальної поведінки методів тестового контуру API реєстру та розробити автономний мок-сервер для команди розробки.

## 3. Кейс C-2

Конфлікт критеріїв: Більшість критеріїв вимагають адаптивного підходу. Вимоги формуються на основі постійних користувацьких інтерв'ю кожні два тижні, замовник-співзасновник сидить в одній кімнаті з розробниками, зовнішнього контракту немає (є 9 місяців інвесторського runway), релізи щотижневі, а команда крос-функціональна й компактна. Конфліктує з цим лише ціна помилки релізу: помилки в розрахунку комісій і застав призводять до фінансових втрат клієнтів, ручних повернень і ризику розірвання договору еквайрингу банком. Переміг адаптивний підхід, оскільки в стартапі швидкість перевірки гіпотез є вирішальною умовою виживання бізнесу.

Що робимо з критерієм, який тягне проти: Виділяємо платіжні та розрахункові операції в окремий ізольований модуль із обов'язковим 100% покриттям автоматичними тестами, запроваджуємо обов'язкове подвійне код-рев'ю для змін фінансової логіки та ручну верифікацію транзакцій на staging-середовищі перед щотижневою викаткою.

Відкинутий підхід: Предиктивний підхід. Плюс: гарантував би вичерпну попередню специфікацію розрахункових алгоритмів та їхню тривалу стабільність. Мінус: позбавив би стартап можливості швидко змінювати вектор розвитку за результатами інтерв'ю та призвів би до неефективного витрачання бюджету інвестора.

Перший тиждень: Розгорнути пісочницю платіжного провайдера, налаштувати CI/CD конвеєр із блокуванням збірки при падінні тестів і покрити поточні алгоритми комісій базовим набором регресійних тестів.

## 4. Кейс C-3

Конфлікт критеріїв: Проєкт має класичний розрив між жорсткою зовнішньою рамкою та непередбачуваним змістом. З одного боку, контракт fixed price із незмінним річним бюджетом наглядової ради, спонсор-фіндиректор вимагає фіксованих термінів, а помилка у щомісячних розрахунках веде до неправильних виплат контрагентам. З іншого боку, бізнес-процес погодження договорів містить безліч невідомих винятків, які спливають лише на демо, а міграція з 20-річної легасі-системи ускладнена відсутністю документації та брудними даними. Переміг гібридний підхід: предиктивна рамка строків і бюджету для фіндиректора поєднується з адаптивними ітераціями розробки та демонстрацій для юристів.

Що робимо з критерієм, який тягне проти: Керуємо змінами через динамічний беклог: кожен нововиявлений виняток у погодженні договорів додається в поточний реліз виключно шляхом вилучення або перенесення у майбутній реліз іншої функції аналогічної трудомісткості (trade-off обсягу при фіксованому бюджеті).

Відкинутий підхід: Чистий предиктивний підхід (Waterfall). Плюс: чітка фіксація початкового технічного завдання захистила б виконавця від юридичних суперечок із фінансовим директором. Мінус: створена за старим ТЗ система виявилася б нежиттєздатною для юристів, оскільки реальні маршрути договорів кардинально відрізняються від формального положення.

Перший тиждень: Провести технічний аудит і профілювання бази даних старої системи (особливо 12.5% записів без контрагентів) та затвердити з фінансовим директором регламент управління змінами обсягу за правилом trade-off.

## 5. Стрес-тест контрактом

Конверт зі зміною умови: Кейс C-1, контракт стає Time and Material (T&M) з оплатою за фактично відпрацьованими годинами.

| Кейс | Рішення до конверта | Рішення після | Що змінилось у роботі PM |
| :-: | --- | --- | --- |
| C-1 | predictive, main_conflict: technology | hybrid, main_conflict: release_cost | Зміна моделі управління: замість трьох формальних актів приймання впроваджуються двотижневі звіти про спалені години та стан інтеграції з API реєстру. Ризик технічної нестабільності API переїхав із підрядника на замовника. |

Два робочі ходи PM, коли контракт fixed price, а вимоги мінливі:
1. **Фіксований бюджет із гнучким обсягом (Scope Tolerance):** Сторони фіксують бюджет і дедлайн, але в договорі прописують можливість заміни функцій у беклозі за принципом 1:1 за оцінкою трудомісткості. Ціна ходу: замовник отримує не всі спочатку задумані другорядні функції, а PM витрачає час на постійні погодження пріоритетів.
2. **Жорсткий Change Management:** Будь-яка вимога, що виходить за межі початкового ТЗ, фіксується як офіційний Change Request із окремим кошторисом, збільшенням бюджету або перенесенням термінів. Ціна ходу: високий ризик конфліктів із замовником, уповільнення темпів розробки через бюрократичні узгодження та погіршення ділових стосунків.

## 6. Власний проєкт

Тема: Сервіс бронювання аудиторій і обладнання з погодженням заявок.

Обраний підхід: Гібридний підхід (Hybrid). Предиктивним елементом є фіксований строк до релізу (12 тижнів за варіантом V01) та фіксований бюджет (840 000 грн) без можливості виходу за ці межі. Адаптивним елементом є розробка двотижневими спринтами з регулярною зміною пріоритетів у беклозі на основі зворотного зв'язку від студентів і викладачів.

Чому саме так: Команда варіанта V01 обмежена ресурсами (PM 50%, BA 50%, 2 Dev 100%, QA 50%) і має сувору стелю у 12 тижнів. Замовник (навчальний відділ / диспетчери корпусів) доступний періодично, проте кінцеві користувачі потребують частих ітерацій для виявлення неочевидних конфліктів у розкладі. Обраний підхід безпосередньо запобігає **Ризику 1 із розтину ЛР1** (масове одночасне бронювання аудиторій спричинить падіння вебсервісу або дублювання заявок через відсутність стрес-тестування конкурентних запитів). Завдяки ітераціям QA-інженер включає перевірку concurrency-сценаріїв у Definition of Done кожного спринта, виявляючи проблеми задовго до релізу. Від навчальних кейсів наша ситуація відрізняється тим, що ми розробляємо новий вебсервіс із нуля (на відміну від C-3 з міграцією легасі), маємо жорсткий академічний дедлайн початку семестру (на відміну від відкритого стартап-горизонту C-2) і безпосередній контакт із користувачами (на відміну від C-1).

## 7. Робочий журнал

Під час початкового аналізу кейсу C-1 виникла спокуса обрати гібридний підхід через нестабільність і часті зміни тестового API реєстру. Проте детальний розгляд юридичних обмежень (жорсткий тендерний контракт fixed price із суворою пенею за прострочення та незмінний законодавчий строк подання) показав, що замовник не допустить зміни рамок проєкту, тому підхід має бути предиктивним з ізоляцією ризику через емулятор API. У кейсі C-3 навпаки, наявність fixed price контракту спочатку підштовхувала до предиктивного вибору, однак повна невизначеність внутрішніх винятків погодження довела безальтернативність гібридної моделі.
